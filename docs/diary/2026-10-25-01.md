# 2026-10-25: the investigation, and the wire core

## Question

Can an AemiJSON-shaped protobuf package (fast paths, Codable, checking and definition tools) be built, and where should it start?
Result: yes. The plan is `docs/DESIGN.md` and `docs/roadmap/`; the wire core is built.

## Probes (each could fail)

| Claim | Probe | Verdict |
|---|---|---|
| A hand-written fast path on AemiKernel's `Varint` beats swift-protobuf by a wide margin | `docs/research/probes/throughput`: 1,000 users, identical bytes both ways, release, medians of 15 | **Partly.** Encode 1.3 to 1.6x in six runs. Decode: parity until strings are validated by the `AemiKernels` kernel, then 1.4 to 1.9x. The machine was noisy: absolute numbers moved 2.5x between runs. Ratios within a run only (ADR-0005) |
| Varint decoding is the decode bottleneck | same probe, string handling varied | **False.** `String(validating:)` cost 986 µs against 573 µs with kernel validation, and 384 µs with strings skipped. Strings dominate |
| A first run of the hand path was slower than swift-protobuf on decode (0.6x) | repeat | A cold-run artefact; 0.8 to 1.0x thereafter. The first number was not used |
| Codable can carry protobuf field numbers | `docs/research/probes/codable-shape`, a recording `Encoder` | **Only with `enum CodingKeys: Int`.** Synthesized keys have `intValue == nil` (ADR-0004) |
| Codable can carry the wire type | same | **False.** `Int32` for `int32`, `sint32`, `sfixed32` and enums is one call. A descriptor must say (ADR-0004) |
| `Array.span` is usable at the macOS 15 floor | `swiftc -target arm64-apple-macosx15.0` | **False**, needs macOS 26; `RawSpan` compiles (ADR-0002) |
| The reader agrees with `protoc` on accept and refuse | 1,500 seeded mutations, `protoc --decode_raw` as oracle | **Two disagreements I had not predicted the second of.** protoc truncates a tenth varint byte above 1 (predicted) and a tag above 32 bits (found by the test). Both are strict refusals here (ADR-0003) |

## Built and checked

`AemiProtobufCore`, roadmap 0001. Tests were written first against stubs and seen to fail (74 issues), then the implementation.
42 tests pass in debug and in release (`-Xswiftc -enable-testing`).

Mutants, each applied to the green baseline and restored from a copy (`diff -r` against the backup after the run): tenth-byte
guard widened; length-slot not widened; group depth unchecked; UTF-8 check removed; writer not rolled back on a throwing body;
field-number maximum off by one; reader message depth unchecked; `int32` not sign-extended; length bound off by one; end-group
mismatch ignored; writer size limit ignored; zig-zag decode wrong; reader buffer limit ignored; unmatched end-group skipped.
**14 of 14 killed.** One survived the first pass: the group-depth check before the loop is reached only by a group inside a
message already at the limit. A test for that case now exists, and kills it. One mutant first reported "did not compile" because my
script matched the word `error:` in test output; it was rerun by hand and is killed.
