# 2026-10-25 — AemiJSON, swift-protobuf and AemiProtobuf on the same data

The question: for the same logical records, how do the formats and the libraries compare to encode, decode, navigate and carry?
Reproduce with `Scripts/compare.sh all` (about 14 minutes, release, a quiet machine). Source: `Benchmarks/Comparison` (its own
package, so no library depends on another). The tables below are the third full run, made with the final code, after the writer
and packed-path work listed under "What changed since the first run".

## Method

- **Data.** One record shape from AemiJSON's own benchmark model: ten fields, three optional, a list of tags, a nested object.
  Fixed seeds, so every run and every library sees identical values. 2,000 records are the headline size; 1, 100 and 20,000 show
  scaling. Further corpora: 100,000 numbers in four distributions, 20,000 strings in four classes, nested chains, messages of 10
  and 100 declared fields, eight payloads decoded in parallel, and the memory of one 20,000-record decode.
- **Codecs.**
  - JSON: AemiJSON with plain `Codable` and with `@JSONCodable`; Foundation's coders as the incumbent reference.
  - AemiProtobuf: the fast path generated by `@ProtoMessage` (through `ProtobufEncoder`/`ProtobufDecoder`, and the same generated
    code called directly), and the generic `Codable` path (integer `CodingKeys`, no fast path).
  - swift-protobuf 1.39.0: messages generated from the same `.proto` by its own `protoc-gen-swift`, `serializedBytes()` and
    `init(serializedBytes:)`. It has no lazy view, so its "read two fields" and "walk" rows decode the whole message first.
  - Like for like: `json.AemiJSON.macro`, `pb.AemiProtobuf.fast` and `pb.SwiftProtobuf` are all generated code;
    `json.AemiJSON.codable` and `pb.AemiProtobuf.codable` are both generic.
- **Checked before timed.** Every codec round-trips the corpus at setup. AemiJSON and Foundation decode each other's bytes.
  AemiProtobuf and swift-protobuf write byte-identical output for every size and decode each other's bytes. The generic path
  writes the same bytes as the fast path. `protoc --decode=Users comparison.proto` decodes those bytes into 100 well-formed
  users. A failure exits instead of timing broken work.
- **Measure.** ordo-one `package-benchmark`, release, wall-clock p50/p90/p99 over at most 2 s or 50,000 iterations, allocation
  counts. One process, one machine (arm64, 10 cores, 16 GB), benchmarks one after another. Memory is one decode per process
  (`ComparisonMemory`), because a benchmark process has a single peak for all its benchmarks.
- **Noise.** The AemiProtobuf rows repeat to within a few percent between runs. In this run the AemiJSON rows at 20,000 records
  and in the parallel test came out 20–40 % slower than in the previous run, with the same code; the 2,000-record rows did not.
  Treat ratios against AemiJSON at those sizes as lower bounds on its time, and the protobuf-to-protobuf ratios as the firm ones.

## What changed since the first run

The first run (same data) found AemiProtobuf losing on bulk packed data. Each cause was probed before it was changed:

| slow path | before | after | change |
|---|---:|---:|---|
| 100,000 doubles, encode | 628 µs | 13.0 µs | one copy of the little-endian words (`appendPackedLittleEndian`), not eight appends per double |
| 100,000 doubles, decode | 268 µs | 27.6 µs | `readPackedLittleEndian`: one allocation and one copy |
| 100,000 wide integers, decode | 592 µs | 341 µs | `readPackedVarints`: element count from a word-at-a-time scan, then one array, local loop |
| 100,000 wide integers, encode | 558 µs | 523 µs | `appendPackedVarints`: sizes summed first, so no length-prefix shift |
| validating three fields | 5 allocations | 2 | a linear search instead of a dictionary for messages of up to 16 fields |

Probed and left as they were, with the measurement:

- **Varint read.** An isolated loop reads 4,096 varints in 6.4 µs with a local loop and 14.3 µs through AemiKernel's
  `Varint.read`, so the local loop stays. The reader's own `readVarint` costs 19.5 µs in the suite (4.8 ns per varint), three
  times the isolated loop, because it keeps its offset in the struct; no workload here is limited by it.
- **Borrowing `Data`.** Decoding straight from the `Data`'s storage was no faster at 238 KB and 170 ns slower for a 10-field
  message (two extra allocations), so `decode(from: Data)` copies.
- **Many declared fields.** Decode takes 208 ns for a 10-field message and 875 ns for 100: per-field cost falls, so the
  generated field dispatch does not grow with the field count.
- **String encode.** A fused tag-length-bytes call and an exact up-front size gave no gain (a sized buffer made one allocation
  instead of twelve and was not faster), and `withUTF8` was 21 % faster in an isolated loop and no faster in place. The gap to
  swift-protobuf (1.7–1.9×) is not allocation or call overhead; it is the per-append bookkeeping of `Array` against swift-protobuf's
  raw-pointer writes into a buffer it sized first (roadmap 0019). The same applies to the 1.3–1.5× integer-encode gap.
- **Parallel scaling.** An allocation-free reader scales 3.7× for eight tasks, as the decodes do (3.8×), so the 3.6–4.3× is the
  machine (not 10 equal cores), not the allocator.

## What the numbers say, and what they do not

1. **On message-shaped data the generated fast path beats both rivals.** It encodes 2.3× and decodes 1.26× faster than
   swift-protobuf, and 2.6× and 2.0× faster than AemiJSON's own macro, with 12 allocations to encode 2,000 records where
   swift-protobuf makes 4,001 and the AemiJSON macro 2,002. It also holds the smallest decoded result: 9.3 MB against 12.9 MB
   (swift-protobuf), 15.4 MB (AemiJSON macro) and 22.4 MB (Foundation).
2. **On bulk packed numbers AemiProtobuf now leads for doubles and wide-integer decode and trails swift-protobuf on integer encode**
   by 1.3–1.5×; strings are 1.7–1.9× slower to encode and 1.1–2.1× faster to decode.
3. **The generic `Codable` path is the weak spot.** It encodes 1.8× faster than AemiJSON's generic path and decodes 1.7× slower,
   with about 8× the allocations; its retained memory is close to the fast path's (10.8 MB). Roadmap 0018. A type that matters
   uses `@ProtoMessage`, which is why the macro is the main API.
4. **Untyped reading favours AemiProtobuf most**: the lazy reader needs no tape and no decoded message (6.5× against
   swift-protobuf's decode-then-read, 4.3× against AemiJSON's tape). `countRecords` reads only top-level framing and is not a
   counterpart of AemiJSON's `parse`; the validating walk is.
5. **Foundation is the slowest in nearly every row** and allocates 10 to 100 times as often.

## Limits of this comparison

- One machine, one operating system, no Linux, no device. Wall clock, plus the memory table above.
- Allocation counts above 1,000 are printed to three digits by the tool and are approximate (`~`).
- swift-protobuf is used as generated with default options. Its JSON and text formats, reflection and `Any` are not measured.
- Not compared yet: streaming and framing (built, roadmap 0009, but not benchmarked against anything), schema definition,
  compression, any network effect. Smaller bytes do not by themselves mean a faster service.
- `map` and `oneof` are not exercised: neither the macro nor the generic path supports them yet.
